# Spec: Keep awake while agents work, and approval alerts (v0.2)

Status: draft · Target: v0.2.0 · Platform: macOS (no-op elsewhere unless stated)

## Summary

Two additions to Agent Status:

1. **Keep awake.** While at least one agent is working, the Mac does not go to idle sleep. The screen may still turn off and lock, and agents keep running behind the lock screen. When no agent is working, normal sleep behaviour returns.
2. **Approval alerts.** When any session waits for a permission decision, every Agent Status surface shows it clearly: menu bar, dashboard, compact window, desktop widget, terminal view and Stream Deck keys. Clicking an agent still only navigates to its window. Nothing is ever approved from Agent Status.

## Background

- Locking the screen does not pause processes. Idle **system sleep** does: processes freeze and network connections drop, so an agent stops mid-task until the Mac wakes up.
- An agent waiting for a permission decision stops regardless of sleep, until someone answers it in its own terminal.

## Goals

- G1. No idle system sleep while ≥ 1 agent has status `in_progress`, including while the screen is locked.
- G2. Restore normal sleep behaviour automatically once no agent is working.
- G3. Show pending approvals on every surface, with the number of sessions and which ones.
- G4. Clicking an agent in any surface only brings its window or tab to the front.

## Non-goals

- Approving, denying or sending any input to a session from Agent Status.
- Preventing sleep when the lid is closed on battery power, or changing system power settings (`pmset`).
- Push notifications to a phone (planned separately).
- Keep-awake on Linux or Windows.

## 1. Keep awake

### 1.1 Mechanism

The service runs macOS's built-in `caffeinate`:

```
caffeinate -i -w <service pid>
```

- `-i` holds a *prevent idle system sleep* assertion. The display can still sleep and the screen can still lock.
- `-w <service pid>` ends `caffeinate` automatically if the service exits for any reason, so no assertion can outlive the service.
- Releasing the hold = terminating that `caffeinate` process.
- At most one `caffeinate` process exists per service.

### 1.2 When the hold is active

The hold is active when all of these are true:

| Condition | Detail |
|---|---|
| Mode allows it | see 1.3 |
| Someone is working | ≥ 1 agent with status `in_progress` **or** with running subagents |
| Grace period | the hold stays for **60 s** after the last working agent stops, so it doesn't toggle between tool calls |

Statuses `waiting` (needs approval), `retry`, `sleeping` and `done` do not start a hold on their own. A session that is stuck in `in_progress` already turns `sleeping` after `AGENT_STATUS_STALL_MIN` (3 min), which ends the hold.

The decision is a pure function, unit-tested without macOS:

```js
shouldKeepAwake({ agents, mode, power, now, lastWorkingAt }) -> { hold: boolean, reason: string }
```

### 1.3 Modes

| Mode | Behaviour |
|---|---|
| `power` (default) | Hold only while on AC power. Switching to battery releases the hold within one tick (15 s). |
| `always` | Hold on AC and battery. |
| `off` | Never hold. |

Power source: `pmset -g ps`, first line contains `AC Power` or `Battery Power`, read every tick (15 s). Desktop Macs report `AC Power`.

### 1.4 Configuration

Stored in `~/.claude/agent-status/config.json` (or `$AGENT_STATUS_DIR/config.json`):

```json
{ "keepAwake": "power", "systemNotifications": true }
```

- Read at service start; changes through the API apply immediately and are saved.
- `claude-s awake [power|always|off]`: prints the current mode and state; with an argument, sets the mode.
- `GET /api/config` returns the config; `POST /api/config` (JSON) updates known keys; unknown keys and invalid values return 400.

### 1.5 State exposed

Added to `GET /api/agents` (and the SSE stream):

```json
"keepAwake": { "mode": "power", "active": true, "since": 1793180000000, "power": "ac", "reason": "2 agents working" }
```

`reason` examples: `"2 agents working"`, `"grace period (40 s left)"`, `"no agent working"`, `"on battery (mode: power)"`, `"mode: off"`, `"caffeinate not available"`.

### 1.6 Where it is shown

| Surface | Display |
|---|---|
| Menu bar title | `☕` appended while the hold is active, e.g. `⚠1 ●2 ☕` |
| Menu dropdown | Last line: `☕ Keeping Mac awake: 2 agents working`, or `Sleep allowed: no agent working`. Submenu with the three modes (current one checked), each runs `claude-s awake <mode>` |
| Dashboard / compact | Small chip in the header: `☕ Awake` with the reason as tooltip |
| `claude-s status` | Footer line: `☕ keeping awake (2 agents working)` |
| `claude-s doctor` | Mode, power source, whether `caffeinate` is available |

### 1.7 Failure handling

- `caffeinate` missing or fails to start: `active: false`, `reason: "caffeinate not available"`, shown in doctor. The rest of the service is unaffected.
- `caffeinate` exits unexpectedly while a hold is wanted: restarted on the next tick.
- Service stops (`claude-s stop`, crash): `caffeinate` exits through `-w`.

### 1.8 Limits (documented in README)

- Closing the lid on battery sleeps the Mac anyway.
- Energy settings can still put the display to sleep and lock the screen. That's expected: agents run behind the lock screen.

## 2. Approval alerts

### 2.1 Definition

A session **needs approval** when its status is `waiting`: a `Notification` hook with `notification_type` `permission_prompt` or `elicitation_dialog`. `idle_prompt` (waiting for the next prompt) is not an approval.

The approval clears on the next `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit`, `Stop` or `SessionEnd` of that session. This is existing status behaviour.

### 2.2 What is shown for an approval

- Project name and slot.
- **What is being approved**: the summary of the tool call that triggered the prompt, taken from the session's most recent `PreToolUse` (e.g. `Bash: npm run lint -- --fix`). Fallback: the notification message.
- Time waiting (since the status became `waiting`).

New service field per agent: `approval: { detail, since }` (present only while `waiting`).
New top-level field: `approvals: [{ id, slot, project, detail, since }]`, oldest first.

### 2.3 Surfaces

| Surface | Display |
|---|---|
| Menu bar title | When approvals > 0: title starts with `⚠ N` in orange (`color=#F5A524`), before the other counts |
| Menu dropdown | Section at the top: **Needs your approval (N)**, one row per approval: `🟠 3. app-3 · Bash: npm run lint · 2m`. Separator, then the regular agent list. Click = navigate only |
| Dashboard | Orange banner under the header: **2 sessions need your approval**, listing project + what + time; each entry clickable (navigate). Existing card highlight stays. Browser tab title `(2) Agents` and a favicon with an orange dot |
| Compact window | Same banner, one line per approval |
| Desktop widget | Header shows `N need approval` in orange; approval rows on top with the detail line |
| `claude-s status` | First line: `⚠ 2 sessions need your approval`, then the list |
| Stream Deck key image | Orange key, label `APPROVE?` under the project name |
| System notification | One macOS notification when a session **enters** `waiting`: title `Approval needed · app-3`, body `Bash: npm run lint`. Shown on the lock screen. Controlled by `systemNotifications` (default `true`). No repeat for the same wait. |

System notifications are sent with `osascript -e 'display notification …'` from the service. Clicking the notification has no action in v0.2.

### 2.4 Click behaviour (all surfaces)

- A click calls the existing focus path: it raises the session's window or tab and does nothing else.
- No keystrokes, no input, no approve or deny is sent to any session. Enforced by a test: the focus code contains no `keystroke`, `key code` or writes to a session's terminal.

## 3. API changes (summary)

| Endpoint / field | Change |
|---|---|
| `GET /api/agents` | adds `keepAwake`, `approvals`, and `approval` per waiting agent |
| `GET /api/config` | new |
| `POST /api/config` | new; body `{ "keepAwake": "power" \| "always" \| "off", "systemNotifications": bool }` |
| `GET /api/swiftbar` | approval section, ☕ indicator, keep-awake submenu |
| `GET /api/slot/N.svg` | orange `APPROVE?` key for waiting agents |

All additions are backward compatible: existing fields and endpoints are unchanged.

## 4. Tests

Unit (no macOS needed):
- `shouldKeepAwake`: each mode × AC/battery × working/not working × inside/outside grace period × subagents only.
- Approval detail: taken from the last `PreToolUse`; fallback to the message; cleared on each clearing event.
- Approvals list order (oldest first) and counts.
- Config: valid values saved and applied; invalid values rejected with 400.

Integration (fake `caffeinate` and `pmset` on `PATH`):
- Hold starts when an agent goes `in_progress`; exactly one `caffeinate` process; it carries `-i -w <service pid>`.
- Hold ends after the grace period once no agent works.
- `power` mode releases on a battery reading; `off` never starts one.
- Stopping the service ends `caffeinate`.
- Menu output contains the approval section and `☕`; clicking a row runs focus only.
- Guard: focus code contains no keystroke or terminal-write calls.
